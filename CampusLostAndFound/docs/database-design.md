# Database Design

This document explains the database used by the Campus Lost and Found
Management System: the schema, the keys, the constraints and the most important
SQL queries.

The full script is in [`database/schema.sql`](../database/schema.sql).

---

## 1. Database

| Property      | Value                       |
|---------------|-----------------------------|
| Name          | `campus_lost_found`         |
| Character set | `utf8mb4`                   |
| Collation     | `utf8mb4_unicode_ci`        |
| Storage engine| InnoDB                      |

Only **one table** is required. A lost-and-found system records a list of
reports; there are no users, categories tables or ownership relationships to
model, so extra tables would add complexity without any benefit.

## 2. Table: `items`

```sql
CREATE TABLE IF NOT EXISTS items (
    item_id      INT            NOT NULL AUTO_INCREMENT,
    item_name    VARCHAR(100)   NOT NULL,
    category     VARCHAR(50)    NOT NULL,
    description  VARCHAR(500)   NULL,
    report_type  VARCHAR(10)    NOT NULL,
    location     VARCHAR(100)   NOT NULL,
    report_date  DATE           NOT NULL,
    contact_info VARCHAR(100)   NULL,
    status       VARCHAR(10)    NOT NULL DEFAULT 'ACTIVE',
    created_at   TIMESTAMP      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   TIMESTAMP      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (item_id),
    CONSTRAINT chk_items_report_type CHECK (report_type IN ('LOST', 'FOUND')),
    CONSTRAINT chk_items_status      CHECK (status      IN ('ACTIVE', 'RECOVERED')),
    INDEX idx_items_name     (item_name),
    INDEX idx_items_category (category),
    INDEX idx_items_type     (report_type),
    INDEX idx_items_status   (status),
    INDEX idx_items_location (location)
) ENGINE = InnoDB;
```

### Field descriptions

| Field          | Type         | Null | Key / Default | Why it exists                                             |
|----------------|--------------|------|---------------|-----------------------------------------------------------|
| `item_id`      | INT          | No   | PK, auto      | Unique identifier generated by MySQL.                     |
| `item_name`    | VARCHAR(100) | No   | index         | Short name of the item ("Blue Wallet").                   |
| `category`     | VARCHAR(50)  | No   | index         | Grouping such as Documents, Electronics, Bottles.         |
| `description`  | VARCHAR(500) | Yes  |               | Optional extra details (colour, marks, contents).         |
| `report_type`  | VARCHAR(10)  | No   | index         | Whether the report is LOST or FOUND.                      |
| `location`     | VARCHAR(100) | No   | index         | Where the item was lost or found.                         |
| `report_date`  | DATE         | No   |               | The date the item was lost or found (not the insert date).|
| `contact_info` | VARCHAR(100) | Yes  |               | Optional phone number or e-mail (blank stored as NULL).   |
| `status`       | VARCHAR(10)  | No   | default ACTIVE| Recovery state: ACTIVE or RECOVERED.                      |
| `created_at`   | TIMESTAMP    | No   | CURRENT_TIMESTAMP | When the row was inserted.                            |
| `updated_at`   | TIMESTAMP    | No   | auto-update   | Automatically refreshed whenever the row changes.         |

### Keys

* **Primary key:** `item_id`. It uniquely identifies every report and is used
  by the update, recover and delete operations. The value is generated by the
  database (`AUTO_INCREMENT`) and returned to Java through
  `PreparedStatement.getGeneratedKeys()`.

### Constraints

* **NOT NULL** on `item_name`, `category`, `report_type`, `location`,
  `report_date`, `status`, `created_at`, `updated_at` - the important fields
  can never be empty at the database level.
* **CHECK** `chk_items_report_type` - `report_type` may only be `LOST` or
  `FOUND`.
* **CHECK** `chk_items_status` - `status` may only be `ACTIVE` or `RECOVERED`.
* **DEFAULT** - a new row is automatically `ACTIVE` and the timestamps are set
  to the current time.

The same rules are also checked in Java (`ItemService.validate`), which gives
friendly messages, while the CHECK constraints protect the data even if
someone edits the table directly.

### Indexes

Indexes are created on the columns used by `WHERE` and `LIKE` clauses in
`ItemDAO.searchItems`: `item_name`, `category`, `report_type`, `status` and
`location`. This keeps searches fast as the table grows.

## 3. How report type and status work together

`report_type` and `status` are **independent**:

| Example row              | report_type | status    | Meaning                                     |
|--------------------------|-------------|-----------|---------------------------------------------|
| A student lost a wallet  | LOST        | ACTIVE    | Still missing.                              |
| A student found a bottle | FOUND       | ACTIVE    | Item is held, owner not yet found.          |
| An ID card was returned  | FOUND       | RECOVERED | It was reported found and has been returned.|

When an item is recovered the SQL only changes `status`:

```sql
UPDATE items
SET status = 'RECOVERED', updated_at = CURRENT_TIMESTAMP
WHERE item_id = ? AND status = 'ACTIVE';
```

Because `report_type` is not part of this statement, a recovered found item
stays a FOUND report. `WHERE status = 'ACTIVE'` also means the same row can
never be recovered a second time - the second call simply updates 0 rows.

## 4. Important SQL queries

**Insert a new report and read back the generated ID**

```sql
INSERT INTO items
    (item_name, category, description, report_type, location, report_date, contact_info, status)
VALUES (?, ?, ?, ?, ?, ?, ?, ?);
```

**Search dynamically** (only the supplied conditions are added; user input is
always passed as a `?` placeholder):

```sql
SELECT ... FROM items
WHERE 1 = 1
  AND item_name LIKE ?      -- "%wallet%"
  AND report_type = ?
  AND status = ?
ORDER BY item_id DESC;
```

**Statistics in one query**

```sql
SELECT
    COUNT(*) AS total,
    COALESCE(SUM(CASE WHEN report_type = 'LOST'  THEN 1 ELSE 0 END), 0) AS lost_total,
    COALESCE(SUM(CASE WHEN report_type = 'FOUND' THEN 1 ELSE 0 END), 0) AS found_total,
    COALESCE(SUM(CASE WHEN report_type = 'LOST'  AND status = 'ACTIVE' THEN 1 ELSE 0 END), 0) AS active_lost,
    COALESCE(SUM(CASE WHEN report_type = 'FOUND' AND status = 'ACTIVE' THEN 1 ELSE 0 END), 0) AS active_found,
    COALESCE(SUM(CASE WHEN status = 'RECOVERED' THEN 1 ELSE 0 END), 0) AS recovered
FROM items;
```

`SUM(CASE WHEN ... THEN 1 ELSE 0 END)` counts matching rows, and `COALESCE`
converts the `NULL` that `SUM` returns on an empty table into `0`.

## 5. Why these design choices

* **Auto-incrementing ID** rather than a name as key: names are not unique.
* **VARCHAR + CHECK instead of ENUM**: easier to read for beginners and still
  fully enforced. (Both are valid for the assignment.)
* **A single table**: the problem has one entity (an item report) with no
  relationships, so normalisation does not call for more tables.
* **Timestamps**: `created_at` shows when a report was filed and `updated_at`
  proves that an edit or recovery actually changed the row.
